# 任务契约与 Review Focus

计划记录实施者不能独自决定的内容，不预写整个实现。仅填写与当前任务相关的项：

- 文件、确切接口名称/参数/返回值、需求固定值；配置或文档用配置键/可观察结果替代函数签名。
- 测试名称和关键断言、验证命令与通过条件。代码正文仅用于接口/断言不能决定的算法或需求固定的精确文案。
- 跨任务用 `Consumes` / `Produces` 引用相邻任务定义的接口，不复制其实现。每个任务有独立可验证结果，每步是一项可检查动作。

提交前检查接口一致性、重复内容与代码块比例，移除不承载决策的描述。不为写计划创建临时实现，不设统一字数或分钟数。L0/L1 或独立 bounded 小任务保留短清单和最窄验证，不强制接口表/代码断言。

## Review Focus

L2+ 或涉及输入/错误边界的改动，检查需求隐含、当前任务测试未覆盖的失败条件。按用户影响最多选五项，不凑数量；每项交给实际修改行为的任务，并在该任务写明输入、关键断言和验证方式。

| 输入 / 失败条件 | 已确认范围内的用户预期 | owning task / 测试 | 证据状态 / 残余风险 |
|-----------------|-------------------------|-------------------|---------------------|
| <具体条件> | <可观察行为> | <任务及现有或计划新增的测试> | planned / verified / unknown + 原因 |

无候选时注明已检查且未发现。计划中新测试只能标 planned，实施后依据实际结果更新；未运行保留 unknown 并交接 Review。

该表是风险/测试交接，不是新验收 owner。已有 criterion 只引用 ID，不复制或改写 statement。合理用户预期可形成风险发现，不自动扩大 scope、修改冻结 criterion 或授权写入。
