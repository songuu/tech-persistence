# ECC (Enterprise Claude Code) sibling-eval

> 评估请求 = compare + pros/cons，**非实施承诺**（[[feedback_sibling_eval_default_compare_not_borrow]]）。本文已做二次评审；外部规模数字属于易漂移背景，不作为借鉴裁决的承重依据。

## TL;DR

- **ECC = 与 tech-persistence 最近的直系同类**：同品类（agent harness 自进化系统）、同目标用户（dev-tooling）、同原语（skills/instincts/memory/hooks/跨 harness parity/continuous-learning 置信度评分）。同源（两者 instinct 链都源自社区 "Homunculus"）。
- **规模/验证度悬殊**：ECC 是高热度公开同类（workflow agent 曾记录 gh api 口径 207,355★ / 31,832 fork；2026-06-05 spot-check GitHub README 当前公开口径为 182K+★ / 28K+ forks，release note 段写 63 agents / 251 skills）。精确 stars/目录计数随时间漂移，本文只把它当"公开验证度很高"的背景事实；裁决不依赖具体数字。TP solo 自用、~30 skills、双运行时、纯文件。
- **裁决：0 borrow / 2 adapt / 11 backlog / 5 reject**（18 候选）。与历史 sibling-eval 一致（gbrain/gsd/claude-mem 均 0 直接借鉴）。
- **最重要 finding 不是"借什么"，是收敛进化**：TP 独立造出了 ECC ~9 个机制，且 TP 版常更确定性/更 code-anchored（4 不可妥协逼出更好选择）。高热度同类与 solo 项目独立收敛到同一批设计 = TP 架构方向的强外部验证。
- **TP 在一个维度领先 ECC**：ECC 虽 11 harness，其**学习层不跨 harness**——observe hook + Haiku daemon 仅 Claude Code；Codex 只挂通用 MCP memory server，作者自述 "zero parity"。TP 的硬非妥协 #1（copyHookLibs + compatReadDirs 双运行时知识层 parity）是该同类**没做到**的。

## 2. 方法论

dynamic workflow（`ecc-sibling-eval`，26 agents，1.85M tok）：7 个 recon agent 并行深挖 ECC 子系统（gh api + 实际源码，非 README 营销）→ 每个候选立即对抗核验（4 不可妥协 + tp_already_has + target_user_fit + P0 痛点，refute-by-default）。

> 透明性：skills-commands 子系统的 3 个 verify agent 未调 StructuredOutput 掉线，其 recon 数据完整，**3 个候选由主循环 grep 自家代码后补判**（C1 承重事实 `propagate-command-changes.js` 命令列表为 CLI 入参非内部手清单、libs 已 glob 派生；adapt#2 gap `validate-codex-plugin.js:382` 只验 .codex-plugin 对 .claude-plugin 零断言——均已 grep 核实）。

> 外部数字边界：ECC stars / fork / skill / agent 数字是时间敏感背景。后续引用必须带 `verified_at` + 命令或来源；没有嵌入命令证据的旧 gh api 数字只能作为"高热度公开同类"旁证，不能承重。

TP P0 痛点（推荐排序依据，[[feedback_research_recommendation_sort_by_user_pain]]）：
- **P0a** documented-claim-vs-code-reality drift（TP #1 回归源，[[documented-claim-vs-code-reality-drift]]）
- **P0b** 注入知识是否真改变行为（语义遵守不可测，[[ADR-022]]）
- **P0c** 跨运行时 parity 维护负担（每个 lib 需 plugin copy + sha sync + validator）
- **P0d** instinct domain 多样性过低（detectPatterns 只产 workflow/debugging/code-style）
- **P0e** enforcement dead-on-arrival（FP 高→学会 `--no-verify`→enforcement 死亡，[[feedback_enforcement_dead_on_arrival_82pct]]）

## 5. 推荐（按 P0 痛点排序，evaluation 非承诺）

> 用户 persona 接受"什么都不做"为合理结果（[[user_workflow_preferences]]）。以下 2 个 adapt 是**全 18 候选里仅有的、过 4 不可妥协且命中 P0 痛点**的；其余 16 为 backlog/reject。即便这 2 个也低紧迫（measure-before-enforce）。

### 优先级 0（零代码，先做）：测量 P0d / 跨项目复现，验证再投入
在 `~/.claude/homunculus/**/instincts/` 与 `~/.codex/homunculus/**/instincts/` 上统计：(a) instinct 文件名前缀 / domain 分布（量化 P0d 严重度）；(b) 当前项目 id（`detectProjectIdentity()`）对应 instinct 是否存在；(c) 同 instinct id 跨 ≥2 distinct project hash 的数量（决定候选 #3 是否永不触发）。纯读文件、零表面。守 measure-before-enforce（[[ADR-022]]/[[ADR-013]]）——**没有这个数据，#2 和 #3 都是盲投**。

### 推荐 #1（P0a，TP #1 回归源）：.claude-plugin manifest validator 断言 + MCP fq-name 守卫
- **what**：`validate-codex-plugin.js` 加对 `.claude-plugin/plugin.json` 的确定性断言——禁 `agents`/`hooks` key（Claude 自动发现，显式声明会被 validator 拒）、要求 commands/skills 为数组、MCP fully-qualified 工具名 <64 字符；配一份 `PLUGIN_SCHEMA_NOTES.md` 记录这些未文档化约束 + flip-flop 历史。
- **why adapt 非 borrow**：不能照抄 ECC test——TP 两个 manifest **要求集相反**（Codex manifest *要求* hooks/mcpServers，Claude manifest *禁止* agents/hooks），须运行时分别实现（沿 TP 既有 runtime-projection 模式）。
- **gap 已 grep 核实（评估时）**：validate-codex-plugin.js:382 仅验 .codex-plugin，对 .claude-plugin **零断言**。下游 `docs/plans/2026-06-05-ecc-adapts.md` 已完成 T1-T4，把该 gap 下沉为 `scripts/plugin-manifest-checks.js` + `scripts/validate-codex-plugin.js` 确定性校验。
- **紧迫度**：低。当前 Claude manifest 已最小合规，最长 MCP fq-name ~55<64——blast radius 潜在非活跃。属"防未来静默 install 失败"的廉价确定性护栏。

### 推荐 #2（P0d，instinct 多样性）：lean `/instinct-mine` repo-convention 采集通道
- **what**：一个 model-driven 命令（类 `/learn`），读 git log + 配置文件，把 repo 约定（commit 前缀、命名风格、测试流、"改 hook 必同步 config+test+docs"）产出为 `source: repo-curation` 的 instinct，填充 detectPatterns 够不到的 git/testing/code-style domain。
- **why adapt 非 borrow**：丢弃 ECC 全部机器（Python daemon + Haiku + 1826 行 instinct-cli.py + auto-promote）；置信度须**折扣进场**（类 instinct-import ×0.8）+ 要 session 确认才升，否则灌爆 12KB 注入预算 + 污染 /evolve 聚类。
- **紧迫度**：低，且**先做优先级 0 测量**。下游 `docs/plans/2026-06-05-ecc-adapts.md` 已补测：P0d 真实但比初判更窄，#2 应收紧为 spike-first；若 mined 输出多为 rules/CLAUDE.md 已手述条目，则本项自我否决。

## 6. 收敛进化 finding（本评估最高价值产出）

TP 在**无任何借鉴**的前提下，独立造出了 ECC 的核心机制，且常更确定性/更 code-anchored：

| 机制 | ECC | TP（独立实现） | TP 是否更优 |
|---|---|---|---|
| instinct 链 observe→evolve | continuous-learning-v2 | 同（同源 Homunculus） | 平 + TP 有 demand-side telemetry |
| 项目身份 git-remote-hash | sha256(remote)[:12] | detectProjectIdentity | 平 |
| 路径分级 FP 抑制 | RuntimeConfidence 7 级 | knowledge-drift classifyReference | TP 更确定性（二元 gate vs 0.25× 模糊分） |
| 秘钥正则扫描 | governance-capture | secret-scan-on-demand + isLikelyExample | 平 |
| context-budget 仪表 | 静态 words×1.3 估计 | renderContextCostSummary | **TP 更准**（真实 char 分配器读数） |
| hook gating in-code | isHookEnabled 纯函数 | hook-registry.js（[[ADR-014]]） | 平 |
| regenerate-and-compare drift | harness-adapter-compliance | checkPropagateSync / knowledge-drift | **TP 更优**（doc-vs-code/byte，ECC doc-vs-doc） |
| per-session 摘要 | raw transcript .tmp | evaluate-session 从 observations | **TP 更高信号**（结构化非 raw） |
| fail-open hook + 标记 | `[Hook] failed:` | hook-exit-codes.md `[name] failed:` | 平 |

**结论**：一个高热度同类与一个 solo 项目独立收敛到同一批设计——这是 TP 架构方向（4 不可妥协）正确性的强外部验证。差异处 ECC 全是 maximalism（大规模 skills / 11 harness / SQLite / GUI / daemon / 102 规则），正是 TP lightweight-first 该拒的。

**TP 领先点**：ECC 虽 11 harness，**学习层不跨 harness**（observe + Haiku daemon 仅 Claude；Codex 挂通用 MCP server，作者自述 "zero parity"）。TP 硬非妥协 #1（copyHookLibs + compatReadDirs 双运行时知识层 parity）是 ECC **没做到**的——TP 用"少 harness 换深 parity"，ECC 用"多 harness 换浅 parity"，是定位差异不是优劣，但说明 TP 的 parity 严格度在该品类罕见。

**自家代码先行**（[[feedback_grep_self_codebase_before_analysis]]）：承重事实（propagate 命令源、validate 断言范围、secret-scan 已存在、renderContextCostSummary 已存在、classifyReference 已存在）均经 grep/工作流引用核实，非凭记忆。✅

**可能错的地方 / 残余风险**：
1. **adapt#1 紧迫度可能被高估**：若 TP 永不向 .claude-plugin 加 agents/hooks/长 MCP 名，该断言永 trivially pass（同候选 #10 VERSION 的"未验证即上线"问题）。落地时必须配 break-impl 负样本（[[feedback_negative_sample_3_archs]]）证明它真拒。
2. **adapt#2 可能产冗余**：solo 约定多已在 rules/CLAUDE.md；挖出的 repo-curation instinct 可能与手述规则重复。**优先级 0 测量是闸**——不测就做有违 measure-before-enforce。
3. **外部规模数字会漂移**：stars / fork / skills / agents 不参与裁决；后续若要保留精确数字，必须落 `verified_at` + 命令输出。

## 9. 2026-07-30：Codex × Claude Code 原生能力重评

本节不是重做 2026-06-05 的 sibling-eval，而是回答新的架构问题：在 Codex 与 Claude Code 都已拥有更完整原生 agent runtime 后，ECC 与 tech-persistence 应分别承担什么职责。易漂移能力只采用当前一手文档，不用 stars、目录规模或营销数字承重。

### 9.1 已验证事实

1. ECC `main` README 仍把 Codex hook events 标为 `None yet`，但当前 Codex 已正式提供 session、subagent、tool、compact 等生命周期 hooks，Codex plugin 也可以原生打包 hooks。ECC 的这部分 parity 表已滞后，不能再作为 adapter 设计依据（[ECC README](https://raw.githubusercontent.com/affaan-m/ECC/main/README.md)、[Codex hooks](https://learn.chatgpt.com/docs/hooks)、[Codex plugin structure](https://developers.openai.com/plugins/build/plugins)）。
2. ECC 的 Codex plugin notes 承认插件目录依赖仓库父级内容，而官方 plugin path rule 要求资源位于插件根内并使用相对路径。正确方向是生成自包含包，不是把手工复制当兼容层（[ECC Codex plugin notes](https://raw.githubusercontent.com/affaan-m/ECC/main/.codex-plugin/README.md)、[Codex plugin path rules](https://developers.openai.com/plugins/build/plugins#path-rules)）。
3. ECC2 的官网/release notes 与 `ecc2/README` 对成熟度表述不一致；入口源码已经出现 delegation、backlog、merge queue、schedule、remote dispatch 等 Operator 命令，但没有在本次评估中进行 build、运行和故障注入。因此可确认“产品面在扩张”，不能确认生产成熟度（[ECC 官网](https://ecc.tools/)、[ECC 2.0 release notes](https://raw.githubusercontent.com/affaan-m/ECC/main/docs/releases/2.0.0/release-notes.md)、[ecc2 README](https://raw.githubusercontent.com/affaan-m/ECC/main/ecc2/README.md)、[ecc2 main.rs](https://raw.githubusercontent.com/affaan-m/ECC/main/ecc2/src/main.rs)）。
4. Codex 当前原生提供 subagents/TOML agents、hooks、managed worktrees/Handoff、持久 thread、Goal、App Server、`exec resume`、JSONL/JSON Schema 与 plugins；Claude Code 当前原生提供可恢复/嵌套 subagents、worktree isolation、hooks、`--json-schema`、session resume/fork、Goal、auto memory，Agent Teams 仍属实验能力（[Codex subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Codex App Server](https://learn.chatgpt.com/docs/app-server)、[Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)、[Claude subagents](https://code.claude.com/docs/en/sub-agents)、[Claude worktrees](https://code.claude.com/docs/en/worktrees)、[Claude hooks](https://code.claude.com/docs/en/hooks)）。

### 9.2 全面对比矩阵

| 维度 | Codex / Claude 原生基线 | ECC | tech-persistence（本轮后） | 裁决 |
|---|---|---|---|---|
| 定位 | 两个完整 agent runtime | 广覆盖内容分发、安全扫描、Operator 产品 | 双原生跨 Provider 事务与证据内核 | TP 不应复制 ECC 的通用 harness 层 |
| Agents / Subagents | 两端均有原生角色、并发与生命周期 | Claude 目录丰富；Codex 适配较浅；ECC2 有外层 delegate/team | 各自投影 explorer/implementer/reviewer，宿主拥有 worker 生命周期 | 保留原生 agent，外层只绑定角色/证据 |
| Worktrees | Codex managed worktree/Handoff；Claude CLI 与 subagent isolation | 有 worktree、merge queue、board 命令面，成熟度未验证 | 能绑定 workspace、diff、handoff，但不是完整 manager | 当前最大功能缺口之一 |
| Hooks | 两端均有原生 lifecycle hooks | Claude 强；Codex 对比表已过时 | Codex 只采集四类 allowlisted、bounded、idempotent evidence | TP 的 Codex 适配当前更贴近官方能力 |
| Skills / Plugins | 两端结构、作用域、信任模型不同 | 内容广；Codex 包存在父级引用脆弱性 | Claude canonical skills 与 commands；Codex native overrides + generated wrappers；包内 parity validator | 坚持 shared core + native overlay + self-contained package |
| Structured output | Codex output schema/JSONL；Claude JSON schema/JSON event stream | 未找到跨 Provider 终态 schema 验收证据 | provider flag + 本地 strict schema 复验 + canonical result acceptance | TP 更强；本地复验是纵深防御 |
| Session / Thread resume | 两端均有原生 resume/fork | ECC2 有外层 resume，是否恢复原生 ref 未证实 | 保存 opaque session/thread ref；仅同 runtime/provider/stage native resume，否则 reconcile | 不复制 transcript，只存 opaque ref |
| App Server / Agent SDK | Codex App Server、Claude Agent SDK 是机器接口 | 未找到明确集成 | Codex App Server 仅 opt-in prepare-only；Claude 以 CLI 为主 | 下一阶段应让 adapter 更薄 |
| Goal | Codex thread Goal；Claude session Goal | 未找到双 Provider Goal 绑定证据 | 外部 host Goal lease + revision CAS + run lock；原生 Goal 只作 opaque host ref | 外部 Goal 管跨 Provider authority，原生 Goal 管线程续跑 |
| 并发控制 | 各 runtime 管内部 agent 并发 | ECC2 有 backlog/rebalance/queue 形态 | provider-dispatch、Goal mutation、single-writer；稳定 lexical control identity | 仍缺 host/provider/worktree 四层容量调度 |
| Handoff | Codex 可搬运 chat+Git；Claude 绑定 session/worktree | Memory Vault/session handoff 思路完整 | redacted hash-bound task/result/handoff、artifact realpath、diff/content digest、stale revalidation | 跨 Provider handoff 是 TP 核心，不能由原生 handoff 替代 |
| Failure recovery | 两端有 native resume/cancel | 未找到 accepted/partial-effects 的明确跨 Provider语义 | accepted canonical artifacts immutable；partial/unknown 只 resume 或 reconcile，禁 silent fallback | TP 的事务边界更强 |
| Memory / Learning | Claude auto memory；Codex memories | instincts、置信度、衰减、evolution、central registry | governed memory、compound、instinct、显式 durable write | 需补 native memory provenance/冲突策略 |
| Operator / Observability | Provider 各自 UI/event stream | TUI、SQLite、session/worktree/queue 产品愿景更完整 | evidence ledger 强，Operator UI/merge queue 弱 | ECC 最值得借鉴的层 |
| Distribution lifecycle | 两端均有 plugin/marketplace trust 边界 | profile、dry-run、doctor、repair、uninstall、install-state 更完整 | 双 Provider build/projection/parity 强，安装状态生命周期较弱 | 借治理，不借父级引用布局 |
| Security | sandbox、approval、plugin/hook trust | AgentShield 偏配置/MCP/prompt/secret 静态审计 | fail-closed 路由、外部锁/CAS、realpath、摘要、脱敏偏执行安全 | 两者互补 |
| Harness breadth | 各自深度最佳 | 多 harness | 专注 Codex + Claude | 当前用户目标下，深度优先于平台数量 |

### 9.3 最终边界

- **Provider 原生负责**：agent loop、subagents、单 Provider worktree、hooks、session/thread、structured output、线程内 Goal。
- **tech-persistence 负责**：冻结 contract、跨 Provider route、全局 writer/lease/CAS、跨 Provider handoff、证据 acceptance、governed memory。
- **Operator 层负责**：可视化、队列、merge、doctor、install state、静态安全扫描；不得重做 Provider agent loop。

### 9.4 ECC 可借与不借

**可借**：doctor/repair/uninstall/install-state，AgentShield 类静态配置审计，session/worktree board 与 merge queue，reviewable learning promotion/rollback，Memory Vault 的“未审查上下文”标记，机器可执行 adapter matrix。

**不借**：以 Claude payload/目录作为所有 harness 的标准、用文件复制证明兼容、父级路径插件、手工 README parity 表、默认加载大量 skills/MCP、hook 自动晋升 durable memory、把 lock/Goal 放在 provider workspace、重做 App Server/Agent SDK/native resume 内部状态机。

### 9.5 当前缺口与优先级

1. **P0**：Codex App Server 仍是 prepare-only；需要真实 initialize/capability、thread start/resume/fork、turn/interrupt、Goal、event 与 approval adapter，`codex exec` 保留 CI fallback。
2. **P0**：Claude 仍以 `-p` 为兼容安全默认；需要验证 deterministic `--bare` 或 Agent SDK 路径，并显式注入 settings/agents/plugins，而不是继承未知本机状态。
3. **P1**：补原生 worktree adapter；外层只管跨 Provider merge queue 与 writer exclusivity。
4. **P1**：能力探测改用 Claude init capabilities 与 Codex App Server feature/model APIs，减少静态 profile。
5. **P1**：统一 host 总并发、Provider 并发、workspace writer、worktree 数量四层配额。
6. **P1**：定义 `native-off / native-read / native-write / governed-only` memory provenance 策略。
7. **P1**：补真实 provider canary，覆盖 schema、resume、subagent hooks、Goal、cancel、failure recovery 与 Windows junction/worktree。
8. **P2**：再补 Operator dashboard、merge queue、安装状态与 AgentShield 类供应链扫描。

### 9.6 推断与未知项

- **推断**：对于“更好结合 Codex 与 Claude Code 原生能力”这个目标，TP 应作为主执行内核，ECC 更适合作为 Operator、安装治理和静态安全参考。原生能力越丰富，外层越应只保留跨 Provider 不变量和事务边界。
- **未知项**：ECC2 没有经过本地 build/运行/故障注入；在已检查入口中也未证实 Codex App Server、双 Provider 原生 Goal、Provider JSON Schema 终态验收集成。这里是“未证实”，不是断言不存在。
- **未知项**：Agent Teams 仍是实验能力，不进入核心依赖；live paid-provider、真实 resume/Goal/cancel 和长时间竞争压力也不在本轮离线验证范围内。
